# خطة التعدد اللغوي والتطبيق المحمول — عربية (Arabya)

آخر تحديث: 2026-07-24  
الحالة: خطة تنفيذية (ليست تنفيذًا كاملًا بعد)

---

## 1) الهدف

جعل **عربية** منتجًا متعدد اللغات من الواجهة وحتى المحتوى القرآني (ترجمات الآيات، ترجمة الكلمة، التفاسير حيث ينطبق)، مع مسار واضح لتحويل الويب إلى تطبيقات **Android** و**iOS** دون كسر نموذج «دراسة الكلمة بطبقات + إسناد مصادر».

القيود الحاكمة (من رؤية المنتج):

- لا scraping لمحتوى محمي؛ الاعتماد على APIs مفتوحة أو ملفات مرخّصة.
- طبقات التحليل تبقى واضحة؛ الترجمة طبقة منفصلة عن الصرف/الإعراب.
- Git-first للمحتوى الثابت؛ الحسابات/المزامنة عبر D1 لاحقًا.

## 3) نظام التعدد اللغوي الكامل (i18n)

### 3.1 فصل ثلاثة أنواع من «اللغة»

1. **لغة الواجهة (UI locale)**  
   نصوص الأزرار، القوائم، الرسائل، الصفحات الثابتة (`عن عربية`، الخصوصية…).

2. **لغة دراسة الكلمة (word gloss locale)**  
   ما يظهر في لوحة الترجمة وجدول «الكلمات» (`ar` / `en` / `id` / `ur`…).

3. **طبعة ترجمة الآية (verse edition)**  
   اختيار مستقل (مثل Saheeh International، Diyanet، Kemenag…) — ليست نفس لغة الواجهة بالضرورة.

> الخطأ الشائع: دمج الثلاثة في مفتاح واحد. يجب إبقاؤها منفصلة في الحالة والتفضيلات.

### 3.2 البنية المقترحة للملفات

```text
locales/
  ar.json          # واجهة عربية (المصدر)
  en.json
  id.json
  ur.json
  tr.json
  …
messages/          # أو next-intl / FormatJS
src/i18n/
  config.ts        # locales, defaultLocale, RTL map
  request.ts
  navigation.ts    # Link/redirect واعي بالمسار
```

محتوى البيانات يبقى في `data/` (ترجمات الآيات، إعراب…) ولا يُخلط مع ملفات واجهة i18n.

### 3.3 المكتبة والأطر (موصى به للويب)

| الخيار | مناسب؟ | ملاحظة |
|--------|--------|--------|
| **next-intl** | نعم (مفضل) | تكامل ممتاز مع App Router، مسارات `/en/...`، رسائل JSON |
| next-i18next | متوسط | أقدم / Pages Router أكثر |
| حلول يدوية | لا للمدى الطويل | يصعب صيانة الـ RTL والمسارات |

### 3.4 المسارات والـ SEO

- النمط المقترح: `arabyaai.com/ar/mushaf/1` و `arabyaai.com/en/mushaf/1`
- `ar` افتراضي؛ إعادة توجيه ذكية حسب `Accept-Language` + تفضيل محفوظ.
- `hreflang` في metadata لكل صفحة فهرسة.
- المصحف والكلمات العربية تبقى بالنص القرآني (عثماني) بغض النظر عن لغة الواجهة.

### 3.5 RTL / LTR

- خريطة: `ar, ur, fa, … → rtl` ؛ `en, id, tr, … → ltr`
- ضبط `dir` و`lang` على `<html>` حسب locale الواجهة.
- مكوّنات الدراسة (المصحف) تبقى RTL داخليًا حتى لو الواجهة LTR (شريط جانبي LTR + مصحف RTL).

### 3.6 مراحل تنفيذ الواجهة متعددة اللغات

**المرحلة A — أساس (1–2 أسابيع)**  
- إدخال next-intl + locale `ar`/`en` فقط.  
- استخراج نصوص الهيدر/الفوتر/الأخطاء.  
- الإبقاء على المصحف عربيًا كما هو.

**المرحلة B — لغات الجمهور (2–4 أسابيع)**  
- `id`, `ur`, `tr`, `fr`, `en` واجهة كاملة.  
- ربط تسمية طبعات الترجمة بـ `nameNative` (منجز جزئيًا في الفهرس).

**المرحلة C — تفضيلات موحّدة**  
- مفتاح سحابي عبر `/api/sync` (locale + meaningLang + verseEdition).  
- واجهة الحساب لإدارة اللغة.

**المرحلة D — محتوى تحريري**  
- صفحات عن/خصوصية/خدمات بلغات متعددة (ملفات MDX أو JSON لكل locale).

### 3.7 ترجمة الكلمة مقابل ترجمة الآية

- توسيع WBW: اليوم `en/id/ur` فقط من API؛ أي لغة جديدة تحتاج مصدرًا مرخّصًا أو حقلًا جديدًا في JSON السور.  
- لا تخترع معاني عربية «كلمة بكلمة» من نماذج دون مصدر.  
- جدول الكلمات يجب أن يعرض دائمًا مبدّل لغة المعنى (منجز في هذه الجولة) حتى لا يختلط مع أوضاع الصفحة.

## 4) تحويل المشروع إلى تطبيق Android و iOS

### 4.1 الخيارات الاستراتيجية

| المسار | الفكرة | متى يناسب عربية؟ |
|--------|--------|------------------|
| **A. PWA / TWA** | تغليف Next.js كتطبيق عبر Trusted Web Activity / Shortcuts | أسرع إطلاق؛ محدود بإشعارات/متاجر أحيانًا |
| **B. Capacitor** | WebView + إضافات أصلية حول نفس الواجهة | مشاركة أقصى كود مع الويب |
| **C. Flutter** | تطبيق أصلي متعدد المنصات بلغة واحدة (Dart) | تجربة موبايل أقوى؛ إعادة بناء UI الدراسة |
| **D. أصلي مزدوج** | Kotlin + Swift | أعلى جودة منصة؛ أعلى تكلفة |
| **E. React Native / Expo** | مشاركة منطق JS؛ UI أصلي تقريبًا | وسط بين Capacitor وFlutter |

### 4.2 توصية عملية لعربية (مرحلية)

1. **الآن → 3 أشهر:** تحسين الويب + PWA جيدة (أوفلاين للمصحف المخزّن، اختصار للشاشة الرئيسية).  
2. **بعد ثبات الطبقات الست والـ i18n:**  
   - إن كان الهدف «نفس تجربة الويب بسرعة» → **Capacitor**.  
   - إن كان الهدف «تطبيق قراءة/دراسة بمستوى تطبيقات المصحف الكبرى» → **Flutter** مع API/حزمة بيانات مشتركة.  
3. **لا تبدأ** بمسارين أصليين (Kotlin+Swift) قبل إثبات المنتج.

### 4.3 مشاركة البيانات مع الموبايل

- حزم `data/translations`, `data/irab`, صفحات المصحف كـ **assets** أو تحميل تدريجي من CDN/Workers.  
- نفس Word IDs وClaims لاحقًا عبر مواصفات `docs/spec`.  
- المصادقة والمزامنة عبر Sync Worker الحالي.

### 4.4 متطلبات متاجر التطبيقات

- سياسة خصوصية، حذف الحساب، توضيح مصادر القرآن/التراجم.  
- عدم إعادة نشر كتب بانتظار ترخيص.  
- أيقونات، لقطات شاشة، دعم RTL في المتاجر العربية.

## 5) Flutter بلغة واحدة أم منصتان أصليتان؟

### 5.1 Flutter (لغة واحدة للكود)

**المميزات**

- كود واحد لـ Android و iOS (وغالبًا ويب/سطح مكتب لاحقًا).  
- أداء UI ممتاز للقوائم الطويلة (صفحات المصحف، جداول الكلمات).  
- نظام i18n ناضج (`flutter_localizations` + ARB).  
- تحكم كامل في اللمس، التمرير، المشغّل الصوتي في الخلفية.

**العيوب**

- **لا يعيد استخدام** مكوّنات React/Next الحالية؛ يحتاج إعادة بناء شاشات الدراسة.  
- حجم الفريق يحتاج معرفة Dart.  
- بعض التكاملات الأصلية (مدفوعات متقدمة، إضافات نادرة) تتطلب قنوات منصة.

### 5.2 لغتان أصليتان (Kotlin + Swift)

**المميزات**

- أقصى استفادة من Human Interface / Material ووصولية النظام.  
- أفضل دعم طويل الأمد لميزات OS الجديدة.

**العيوب**

- تكلفة مضاعفة تقريبًا (ميزتان، باجان، مراجعة مزدوجة).  
- خطر تباعد السلوك بين المنصتين (خصوصًا منطق طبقات الكلمة).  
- غير ملائم لفريق صغير في مرحلة ما قبل اكتمال المنتج الأساسي.

### 5.3 Capacitor / RN مقابل Flutter باختصار

| | Capacitor | React Native | Flutter |
|--|-----------|--------------|---------|
| إعادة استخدام arabya-web | عالية | متوسطة (منطق لا UI) | منخفضة للـ UI |
| إحساس أصلي | متوسط | جيد | ممتاز |
| جهد أول تطبيق | الأقل | متوسط | أعلى في البداية |
| ملاءمة مصحف تفاعلي ثقيل | جيد إن حُسّن الأداء | جيد | ممتاز |

**الخلاصة:** لفريق عربية الحالي (Next.js أولًا): ابدأ بـ **PWA ثم Capacitor** للإطلاق السريع؛ خطط لـ **Flutter** إذا أصبح الموبايل القناة الأساسية للنمو وظهر أن WebView يحدّ تجربة الدراسة/الصوت.

## 7) معايير قبول (Definition of Done) للتعدد اللغوي

- [ ] كل نص واجهة ظاهر للمستخدم يمر عبر مفاتيح i18n (لا نصوص عربية مضمّنة في المكوّنات الحرجة).  
- [ ] `dir`/`lang` صحيحان لكل locale.  
- [ ] اختيار لغة المعنى منفصل عن طبعة الآية وعن لغة الواجهة.  
- [ ] أسماء طبعات الترجمة تظهر بلغتها الأصلية في القوائم.  
- [ ] تغيير لغة المعنى يوضَّح بتنبيه ويرتبط بجدول الكلمات.  
- [ ] لا كسر لـ RTL المصحف عند واجهة LTR.

## 8) مخاطر يجب تجنبها

- ترجمة واجهة آلية دون مراجعة بشرية للمصطلحات الشرعية/النحوية.  
- خلط «تفسير» مع «ترجمة» في نفس المفتاح.  
- تخزين مئات الطبعات دون حاجة (حجم المستودع ووقت البناء) — أضف حسب الطلب/الجمهور.  
- بناء تطبيقين أصليين قبل اكتمال طبقات الكلمة الست.

## 10) القرار الحالي المقترح للمالك

1. اعتماد **next-intl** للويب كممر إلزامي قبل أي تطبيق.  
2. الإبقاء على توسيع **ترجمات الآيات** عبر Quran.com بأسماء أصلية (جاري).  
3. اختيار **Capacitor** لأول تطبيق متاجر إن لزم إطلاق سريع؛ مراجعة **Flutter** عند ثبوت أن الموبايل هو المنتج الأساسي.
