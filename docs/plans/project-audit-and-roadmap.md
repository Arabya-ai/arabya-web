## 0) الخلاصة التنفيذية

المشروع **غني وظيفيًا** (مصحف، دراسة كلمة، صوت، حساب، استوديو، مزامنة D1) لكنه **أحادي اللغة في الواجهة** و**متراكم في مكوّنات ضخمة** و**مربوط بملفات JSON ضخمة (~148MB)**.

قبل بدء next-intl أو Capacitor/Flutter يجب إغلاق عوائق قصيرة (P0) ثم إعادة هيكلة خفيفة (P1) ثم مسار التعدد اللغوي (P2) ثم غلاف الموبايل (P3).

| الحالة الآن | التفاصيل |
|-------------|----------|
| Lint | 0 أخطاء · 6 تحذيرات (متغيرات غير مستخدمة) |
| Tests | كان يفشل 5 اختبارات بسبب `ResizeObserver` في `StudyModeTabs` — يُعالَج في نفس الجولة |
| validate-data | ناجح (114 سورة) |
| CI | lint → test → validate-data → build (بدون e2e / بدون Worker) |

### 1.3 عوائق هيكلية أمام التعدد اللغوي

| # | العائق | التفصيل |
|---|--------|---------|
| I1 | لا يوجد next-intl ولا مجلد `locales/` | كل نصوص الواجهة عربية مضمّنة |
| I2 | `<html lang="ar" dir="rtl">` ثابت في `layout.tsx` | يمنع LTR للواجهات الإنجليزية |
| I3 | كثافة نصوص عربية في: SiteChrome · MushafPageStudio · WordStudyDock · لوحة التحكم | يجب استخراجها قبل ترجمة الواجهة |
| I4 | خلط محتمل بين ثلاثة مفاهيم لغة | **لغة الواجهة** ≠ **لغة ترجمة الكلمة** ≠ **طبعة الآية** — النموذج موجود جزئيًا ويجب عدم دمجه |
| I5 | `manifest.ts` وOG عربية فقط | يحتاجان locale لاحقًا |

### 1.4 عوائق أمام التطبيق المحمول

| # | العائق | التفصيل |
|---|--------|---------|
| N1 | لا Service Worker / PWA حقيقي | Manifest فقط |
| N2 | بيانات `/data` ≈ **148MB** و3550 ملف | لا تُحمّل داخل حزمة التطبيق كاملة |
| N3 | العميل يستدعي `/api/...` مباشرة | Capacitor/Flutter تحتاج Base URL أو حزم بيانات |
| N4 | الصوت بدون Media Session / خلفية أصلية | يتوقف عند تعتيم الشاشة في iOS غالبًا |
| N5 | OAuth Google بدون deep links أصلية | يحتاج إعداد scheme للتطبيق |
| N6 | طبقات sticky (هيدر + تبويبات + مشغّل مثبت) | تضغط مساحة القراءة على الشاشات الصغيرة |

### 1.5 مؤجّل عمدًا (ليس خطأً)

- طبقة **البلاغة** — بلا مصادر مرخّصة  
- **حديث / تراث** — placeholders فقط  
- **Claims متعددة** (ADR-0002) — هيكل موجود وغير موصول بالواجهة  
- قراءات غير حفص — `awaiting_license`  
- اشتراكات مدفوعة

## 2) ما الموجود ويجب تطويره أولًا (الوظائف الحالية)

رتّب حسب قيمة المستخدم × جاهزية الأساس:

### الأولوية A — منتج الدراسة (قلب عربية)

1. **تجربة دراسة الكلمة على المصحف**  
   - موجودة: طبقات إعراب · صرف · ترجمة · تفسير الآية + أوضاع الصفحة.  
   - طوّر: توحيد الكاش، إصلاح a11y، تقليل الازدواج المفاهيمي، أداء التحميل.  
   - كيف: تقسيم `MushafPageStudio` ثم اختبارات تفاعلية بسيطة (اختيار كلمة → تبديل طبقة).

2. **الصوت (آية / كلمات / سورة + مشغّل)**  
   - موجود ويعمل على الويب.  
   - طوّر: Media Session، استئناف موثوق، تهيئة للخلفية على الموبايل.  
   - كيف: استخراج `AudioPlatform` واجهة واحدة (web الآن / Capacitor لاحقًا).

3. **ترجمات الآيات متعددة اللغات**  
   - موجودة (24 طبعة بأسماء أصلية).  
   - طوّر: حماية الفهرس من السكربت القديم، واجهة اختيار أوضح (تجميع حسب اللغة).  
   - كيف: قائمة مجموعات `en / id / tr / …` بدل قائمة مسطّحة طويلة.

### الأولوية B — الحساب والمزامنة

4. **حساب المستخدم + مفضلات + أرشيف دراسة + مزامنة D1**  
   - موجود عبر Sync Worker.  
   - طوّر: مفاتيح تخزين موحّدة، مزامنة تفضيلات اللغة لاحقًا، اختبارات عقد `/api/sync`.  
   - كيف: عقد API موثّق + عدم ربط Worker بحزمة Next كاملة على المدى.

### الأولوية C — محتوى مرخّص لاحقًا

5. **كتب الإعراب `/books`** — جاهز للاستيراد عند وصول الملفات.  
6. **القراءات** — فهرس فقط حتى الترخيص.  
7. **Claims** — عند تعدد مصادر جاهزة.

## 3) إعادة التنظيم والهيكلة المقترحة

### 3.1 تقسيم الواجهة (قبل i18n الكبير)

```text
MushafPageStudio (منسّق)
  ├─ MushafToolbar
  ├─ MushafFrame (النص)
  ├─ WordStudyDock
  ├─ StudyModeTabs + ModePanels
  └─ SurahAudioPlayer
```

### 3.2 طبقة مجال مشتركة (قبل Flutter)

```text
packages/arabya-domain/   (أو src/domain أولاً)
  types, word-id, morph-labels, claims stubs
  بدون fs / بدون React
```

### 3.3 عميل API موحّد (قبل Capacitor)

```ts
// src/lib/api-client.ts
getBaseUrl() // '' على الويب · https://arabyaai.com على الأصل
apiGet('/api/translation/...')
```

### 3.4 بيانات الموبايل

- لا تضمين 148MB في التطبيق.  
- تحميل حسب السورة/الصفحة من CDN أو Workers.  
- Manifest للملفات: `{ surahId, edition, url, hash, size }`.

### 3.5 CSS

- فصل `globals` إلى أجزاء مستوردة أو CSS Modules للمجالات الثقيلة.  
- ملف `rtl.css` / متغيرات `dir` لدعم واجهة LTR مع مصحف RTL.

### المرحلة 3 — استعداد الموبايل (بالتوازي أو بعد 2.4)

| خطوة | عمل |
|------|-----|
| 3.1 | `api-client` + متغير بيئة `NEXT_PUBLIC_API_BASE` |

#### مقارنة قرار الموبايل (مرجع سريع)

| | Capacitor | Flutter | Kotlin+Swift |
|--|-----------|---------|--------------|
| إعادة استخدام arabya-web | عالية | منخفضة للـ UI | معدومة |
| وقت أول إصدار | الأقصر | متوسط | الأطول |
| أداء مصحف تفاعلي | جيد مع ضبط | ممتاز | ممتاز |
| تكلفة فريق صغير | منخفضة | متوسطة | عالية جدًا |

**التوصية الحالية:** بعد استقرار i18n على الويب → Capacitor لإطلاق المتاجر؛ فتح مشروع Flutter فقط إذا ثبت أن WebView يحدّ التجربة (صوت خلفية، تمرير ثقيل، إشعارات قراءة).
